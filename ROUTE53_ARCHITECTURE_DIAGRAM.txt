================================================================================
                            DNS RESOLUTION FLOWS
================================================================================

FLOW 1: External User → API
────────────────────────────────────────────────────────────────────────────────
User Browser:          "dig api.domaine.com"
                       │
Recursive Resolver     "Ask 8.8.8.8"
(8.8.8.8)              │
                       │
TLD Nameserver         "Who manages .com?"
                       │
Route53 NS             "I have api.domaine.com"
                       │
Response               "It's 203.0.113.42" ◄─── Alias to ALB
                       │
ALB Load Balancer      Routes to Cluster A/B (EC2 instances)
                       │
EC2 Instance           Runs application on port 8080
                       │
Browser                Receives response


FLOW 2: Bastion Access (SSH)
────────────────────────────────────────────────────────────────────────────────
User Terminal:         "ssh admin@admin.domaine.com"
                       │
DNS Lookup             "admin.domaine.com = ?"
                       │
Route53 Response       "203.0.113.50" ◄─── Bastion Elastic IP
                       │
SSH Client             Connects to 203.0.113.50:22
                       │
Bastion Host           Authenticates + accepts connection
                       │
SSH Session            User connected ✓


FLOW 3: Internal Service Resolution (from EC2)
────────────────────────────────────────────────────────────────────────────────
EC2 Instance:          "nslookup db.internal.domaine.com"
(inside VPC)           │
VPC Resolver           "That's a private zone"
                       │
Private Zone           "db.internal.domaine.com = 10.0.10.20"
                       │
Response               "10.0.10.20" ◄─── Only available inside VPC
                       │
Application            Connects to 10.0.10.20 (RDS)
                       │
Database               Serves queries ✓


FLOW 4: Health Check Monitoring
────────────────────────────────────────────────────────────────────────────────
Route53 Health Check   Runs every 30 seconds
                       │
                       ├─ Check #1: HTTPS ALB /health
                       │  └─ Response: 200 OK ✓
                       │
                       ├─ Check #2: TCP Bastion:22
                       │  └─ Response: Port open ✓
                       │
CloudWatch Metrics     "health-check-status = HEALTHY"
                       │
                       If 3 failures → Alarm triggered
                       If failover configured → Route to secondary

================================================================================
                          KEY METRICS & TARGETS
================================================================================

DNS Resolution Performance:
├─ Route53 Authoritative Query: < 50ms
├─ Recursive Resolver Cache: < 10ms
├─ Public Resolver (8.8.8.8): < 100ms
├─ Global Propagation: 5-10 minutes
└─ Full Propagation: 24-48 hours

Health Check Performance:
├─ ALB Response Time: < 1 second (expected)
├─ Bastion TCP Connect: < 100ms
├─ Health Check Interval: 30 seconds
├─ Failure Detection: 3 × 30s = 90 seconds
└─ Failover Time: < 2 minutes (typical)

TTL Impact:
├─ API (300s): Cached 5 min → Fast failover
├─ Admin (3600s): Cached 1 hour → Stable
├─ Internal (300s): VPC only → No external cache
└─ External (300s): Partner can change quickly

Cost Impact (Monthly):
├─ Hosted Zone: $0.50
├─ Health Checks (2): $1.00
├─ DNS Queries (10M): $4.00
└─ Private Zone: $1.00
   Total: ~$6.50/month


================================================================================
                             ROUTING POLICIES
================================================================================

SIMPLE ROUTING (used for: admin, aden)
├─ Single record per hostname
├─ No health checks
├─ All values returned randomly
└─ Use case: Stable, non-critical endpoints


WEIGHTED ROUTING (used for: api with 100%)
├─ Multiple records per hostname
├─ Weight distribution (e.g., 70/30 for canary)
├─ Health checks supported
└─ Use case: Canary deployment, A/B testing, gradual rollout


FAILOVER ROUTING (optional, not configured)
├─ PRIMARY record (health checked)
├─ SECONDARY fallback
├─ Switches on health check failure
└─ Use case: Active-passive high availability


GEOLOCATION ROUTING (optional, not configured)
├─ Route based on user location
├─ AWS region, country, continent
└─ Use case: GDPR compliance, CDN routing


LATENCY ROUTING (optional, not configured)
├─ Route to lowest latency region
├─ Multiple region endpoints
└─ Use case: Global application distribution

================================================================================
                          DISASTER RECOVERY
================================================================================

Backup Procedures:
┌─ Terraform State
│  ├─ cp terraform.tfstate terraform.tfstate.backup.YYYYMMDD
│  └─ Upload to S3 (encrypted)
│
├─ Zone Export
│  └─ aws route53 list-resource-record-sets > zone-backup.json
│
└─ Documentation
   └─ Keep runbooks + contact list updated

Recovery Procedures:
┌─ Zone Corruption
│  ├─ Restore from backup: terraform apply -var-file="backup.tfvars"
│  └─ Or import previous state: terraform state pull > old.state
│
├─ Complete Zone Loss
│  ├─ Recreate zone: terraform init && terraform apply
│  └─ Wait 5-10 min for propagation
│
└─ Registrar Change
   ├─ Create identical zone in new registrar
   ├─ Update NS at old registrar
   └─ Wait 48h for convergence

Recovery Time Objectives (RTO):
├─ DNS Failover: < 2 minutes (health check + TTL)
├─ Zone Recreation: 5-10 minutes + 24-48h propagation
└─ Full Recovery: < 1 hour (automated via Terraform)

Recovery Point Objectives (RPO):
├─ Configuration: Real-time (version controlled)
├─ State: At apply time (terraform.tfstate)
└─ Data: N/A (Route53 is configuration only)
